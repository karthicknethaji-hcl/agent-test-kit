# File & interface contracts

This is the formal spec that used to exist only as "copy the other agent's
file" in the framework this package was extracted from. Every shape below is
enforced by `agent-test-kit validate` (backed by the JSON Schemas in
`src/core/schema/`), not just documented in prose.

## Per-agent folder layout (`test-suite/agents/<name>/`)

```
test-suite/agents/<name>/
  README.md
  config/
    test-cases.json
    rubrics.js
    invoke-config.js
    scriptChecks.js         # optional
  review/
    test-cases.review.md    # generated by `render`
    rubrics.review.md       # generated by `render`
    review-status.json
  results/
    run-<timestamp>.md      # or .ndjson — written by `agent-test-kit run`
```

Machine-consumed inputs (`config/`), human-review artifacts plus gate state
(`review/`), and this agent's own run output (`results/`) are kept separate
so each can be tracked, gitignored, or reviewed independently — `results/`
in particular used to live in one shared top-level
`.agent-test-kit-results/` directory across every agent, which made
per-agent tracking harder than it needed to be.

Every path above is resolved from exactly one place, `src/core/agentPaths.js`
(`getAgentPaths(agentDir)`) — every module that needs one of these paths
calls into it rather than constructing its own `path.join(...)`.

An existing repo on the old flat layout (`test-cases.json`, `rubrics.js`,
etc. all as direct siblings) must run
`npx agent-test-kit migrate-layout --dry-run` (prints the plan, changes
nothing) followed by `npx agent-test-kit migrate-layout` once — see that
command's own header comment (`src/cli/commands/migrateLayoutCmd.js`) for
its safety guarantees (conflict detection before any write, a verified
backup snapshot, and safe resumability if it's interrupted).

## Per-agent files

### `invoke-config.js`

```js
module.exports = {
  agentName: 'string',                       // required
  createConversationState() { ... },          // required — returns opaque per-conversation state
  async sendMessage(state, action) {           // required
    // ... call your agent however "calling your agent" means in your repo ...
    return {
      rawText: 'string',        // required — the raw model/agent output
      parsed: {} ,               // optional — your own parsed structure, consumed by scriptChecks.js
      parseError: null,          // optional
      clientTraceId: 'uuid',     // optional — threaded to traceResolver / the result row
      systemPrompt: 'string'     // optional — enriches llm_judge prompts and recommendations
    };
  },
  async smokeTestAction() { ... } // optional — one minimal valid `action` for `agent-test-kit smoke`;
                                    // falls back to {content: '...'} if absent
};
```

`action`'s own shape is **never** part of this contract — it's whatever your
agent actually expects (`{content}`, `{mode, ...}`, anything). `test-cases.json`'s
`probe`/`setup` fields are passed straight through to `sendMessage()` without
interpretation.

Auth/session/API-key resolution belongs INSIDE `sendMessage()`'s body, using
your configured `credentialResolver` (see `docs/ARCHITECTURE.md`) — never
hardcoded here.

### `scriptChecks.js` (only required if any rubric is `evaluatorType: 'script_diff'`)

```js
module.exports = {
  '<rubricCode>': function (testCase, rubric, callResult, context) {
    return { pass: boolean, score: number|null, notes: {}, recommendation: string|null };
  }
};
```

This logic is inherently agent-specific — there's no generic "diff" that
works for every agent's output shape, which is exactly why this lives per
agent rather than in the shared evaluator.

### `test-cases.json`

Schema: `src/core/schema/testCase.schema.json`.

```json
{
  "agentName": "string",
  "schemaVersion": "1.0",
  "testCases": [
    {
      "testId": "string",
      "category": "string",
      "rubric": "string (must match a key in rubrics.js)",
      "v1Scope": true,
      "executionMode": "single-turn | multi-turn | dual-conversation | background-scan | repeat-n",
      "probe": {},
      "setup": [],
      "judgeContext": {},
      "expectedBehaviorNote": "string",
      "failureModeNote": "string"
    }
  ]
}
```

### `rubrics.js`

Schema: `src/core/schema/rubric.schema.json`.

```js
module.exports = {
  '<rubricCode>': {
    metric: 'string',
    evaluatorType: 'script_diff | llm_judge | toxicity_scan',
    scale: 'binary | 0-1',            // llm_judge/toxicity_scan only
    threshold: 0.7,                    // llm_judge only, scaled rubrics; default 0.7
    judgePromptTemplate: 'string'      // required for llm_judge/toxicity_scan;
                                         // {{output}}, {{sourceMaterial}}, etc. filled by evaluator.js
  }
};
```

### `review-status.json`

Written/read by `src/core/reviewStatus.js`; enforced by `agent-test-kit run`
(pass `--skip-gate-check` to bypass locally while iterating).

```json
{
  "gate1": { "approved": false, "reviewer": null, "date": null, "notes": "", "approvedContentHash": null },
  "gate2": { "approved": false, "reviewer": null, "date": null, "notes": "", "approvedContentHash": null }
}
```

`approvedContentHash` is an optional `sha256:...` hash (via
`reviewStatus.computeContentHash(agentDir)`) of `test-cases.json` +
`rubrics.js`'s combined content, recorded by whichever skill/step flips that
gate's `approved` to `true`. `reviewStatus.checkGateContentDrift(agentDir,
status)` recomputes the hash and returns the list of approved gates
(`['gate1']`, `['gate1', 'gate2']`, or `[]`) whose recorded hash no longer
matches — `agent-test-kit run`/`validate`/`sync` all call this and print a
note (never block, never reset the booleans) when it fires. A gate with no
recorded `approvedContentHash` (approved before this field existed, or never
stamped) is never flagged.

### `test-cases.review.md` / `rubrics.review.md` (generated — the human-edit layer)

Not hand-authored from scratch: `agent-test-kit render <agent>` writes these
from the current `test-cases.json`/`rubrics.js`; a reviewer edits them
directly; `agent-test-kit sync <agent>` parses them back into JSON/JS,
validates via `src/core/validate.js`'s `validateContent()` — the same schema
checks, rubric cross-references, and `scriptChecks.js` completeness check
`agent-test-kit validate`/`run` apply — and refuses to write anything on any
error, so `sync` can never succeed on content the very next `validate`/`run`
would then reject. `validate`/`run`/`smoke` never read the `.review.md` files
— only `render`/`sync` do, so the actual enforced contract is exactly as
strict as it was before this layer existed. See
`src/core/mdAuthoring/render.js`/`sync.js` and
`docs/SPEC-sink-reliability-and-md-authoring.md` "Feature 2" for the full
field → prose mapping and the round-trip guarantee
(`sync(render(json)) === json`).

Each file starts with three hidden marker comments (never touched by a human
editor):

```markdown
<!-- agent-test-kit:kind:test-cases -->
<!-- agent-test-kit:agent:<agentName> -->
<!-- agent-test-kit:source-hash:sha256:<hash of the JSON/JS this MD was last rendered from> -->
```

`source-hash` is informational provenance only (embedded once, at `render`
time) — `agent-test-kit check-md-staleness <agent>` does **not** rely on it.
Instead, `checkMdStaleness()` fully parses the current `.review.md` and
structurally compares it (deep-equal, not a hash of raw file text) against
the current on-disk `test-cases.json`/`rubrics.js`: if they'd no longer
produce the same content, the pair is stale — whether because a reviewer
edited the `.review.md` body directly (the normal Gate 1 workflow, and the
scenario that actually matters) or because the JSON/JS was hand-edited
bypassing the MD entirely. A hash-of-the-marker comparison can't detect the
first (and far more common) case, since editing the MD body never touches
the JSON or the embedded marker — that's why this check is a full structural
comparison, not a marker lookup. This check is read-only and always exits 0;
`render` also runs it before overwriting an existing `.review.md`, warning
(never blocking) if doing so would discard edits.

## Pluggable adapter interfaces

See `docs/ARCHITECTURE.md` for why each of these exists and what varies per
consuming repo.

- **`judgeClient`**: `async (promptText) => rawResponseText`
- **`resultsSink`**: `{ async write(row), finalize?(runSummary), close?(), verify?(result), preflight?(), getStats?(), getChildren?() }`
  — `write` is required, called once per test case as it completes.
  `finalize` is optional, called once by `runner.js` after every row for the
  run has already been written, with
  `{runId, agentName, totalRun, totalFail, byCategory}` — a sink that only
  needs per-row writes (`jsonFileSink`, an `mcpSink` whose server doesn't
  implement `finalize`) doesn't need it; one that renders a whole-run summary
  (`markdownSink`) does. `finalize` must never throw — `runner.js` wraps the
  call in try/catch and only warns, since a persistence-hook failure must
  never fail an otherwise-complete run.
  `close()` is a separate, optional lifecycle hook for tearing down a
  resource `write`/`finalize` opened (e.g. `mcpSink`'s spawned child
  process) — kept distinct from `finalize` specifically so a `finalize`
  failure can never skip cleanup, and so a `close` failure (also caught and
  warned, in its own try/catch, independently) can never be confused with a
  `finalize` failure. `runner.js` calls it in a `finally` block after
  `finalize`, whether or not `finalize` itself succeeded. It must be
  idempotent (safe to call more than once) and, like `finalize`, must never
  throw.
  `verify` is separate again, used only by `agent-test-kit smoke` to confirm
  a write actually landed if the sink wants to offer that.
  `preflight()` is an optional, cheap up-front reachability probe —
  `runCmd.js` calls it once before running any test case and returns
  `{ ok: boolean, reason?: string }`; a sink with nothing cheap to check
  (e.g. `markdownSink`) just doesn't implement it. It must never throw or
  reject (a bad connection is reported via `{ok: false, reason}`, not an
  exception) — `mcpSink`'s own implementation wraps its tool call in
  try/catch to guarantee this, and `runCmd.js`/`multiSink` additionally
  isolate a misbehaving third-party sink's rejection so it can never take
  down the run (or its sibling sinks in a `multiSink`) even if a sink doesn't
  honor that.
  `getStats()` is an optional post-run accounting hook returning
  `{ attempted: number, failed: number }` for sinks whose writes can fail
  silently (`mcpSink`) — `runCmd.js` uses it to print real persisted/failed
  counts instead of just "done"; a sink that implements neither `describe()`
  nor `getStats()` (e.g. `consoleSink`) gets no persistence-summary line at
  all, same as before this feature existed.
  `getChildren()` is an optional discovery hook (implemented by `multiSink`)
  returning its wrapped sinks array, one level deep — used by
  `agent-test-kit results` to recursively find a query-capable sink inside a
  fan-out (see "MCP results-sink server contract" below).
  `multiSink` fans `write`/`finalize` out across its children (skipping ones
  that don't implement `finalize`), fans `preflight()` out concurrently
  (isolating each child's own rejection into `{ describe, ok, reason? }`
  since each probe is typically an independent network call), and fans
  `close()` out via `Promise.allSettled` so one child's `close()` failure can
  never prevent its siblings from closing their own resources.
  `queryResults(filter)` is **not** part of this base interface — it's an
  extra, sink-type-specific method `mcpSink` exposes only when its connected
  server advertises the optional `query_results` tool (see below). Callers
  check `typeof sink.supportsQueryResults === 'function'` and await it,
  rather than assuming a synchronous `typeof sink.queryResults === 'function'`
  check is enough (capability discovery for an MCP sink requires connecting
  first, which is asynchronous).
- **`credentialResolver`**: `{ async resolve(agentName, varNames) => { resolved, missing } }`
- **`traceResolver`**: `{ async resolve(clientTraceId, agentName) => traceId|null }` —
  `agentName` is passed alongside the id so a real lookup can scope its
  query correctly (a `clientTraceId` alone isn't guaranteed unique across
  agents sharing one trace table).
- **`createResultsSink(agentName, options)`** (the config factory, not the
  sink itself): called with the agent's name, so the zero-config
  `markdownSink` default can fold it into its filename, and an `options`
  object (currently `{ includeNotes }`, wired from `run --notes`) — `run`
  and `results` always pass both arguments; `smoke` passes only `agentName`
  since it has no `--notes`-equivalent flag. A custom override may ignore
  either argument if it doesn't need it, but should accept `options` as
  possibly `undefined` rather than assuming it's always an object.

### Built-in `resultsSink` adapters

| Adapter | Default? | Notes |
|---|---|---|
| `markdownSink` | Yes | Zero-config default: a fresh, timestamped `.md` file per run under this agent's own `results/` folder (`run-<ISO timestamp>.md`) — never overwritten, and no growing-forever single file to scroll through. Three mutually exclusive placement options, in priority order: `filePath` (an exact file) > `resultsDir` (use this directory as-is) > `dir` (legacy: a parent directory under which `.agent-test-kit-results/` is appended — kept for backward compatibility with existing callers). Passing both `dir` and `resultsDir` is a configuration error, not a silently-resolved precedence choice. Zero dependencies. |
| `jsonFileSink` | No | Appends one NDJSON line per row. `resultsDir` places a timestamped file in an agent-scoped folder the same way `markdownSink`'s does; with neither `filePath` nor `resultsDir`, the legacy default is one global file (`.agent-test-kit-results.ndjson`) shared across every agent — kept for backward compatibility, but not the default once a `resultsDir` is available. Zero dependencies. Machine-readable. |
| `consoleSink` | No | No persistence at all — discards every row. |
| `mcpSink` | No | The generic, vendor-neutral persistence adapter — `createMcpSink({command, args, env})` (or `{transport: {type: 'stdio', ...}}` explicitly) spawns **any** local MCP server over stdio and persists via the contract below. This package has zero knowledge of any specific database; `mcp-servers/` in this repo ships two reference servers (Supabase-backed, and a minimal JSON-file example) as independent, separately-published packages — neither is a dependency of this one. `preflight`/`finalize`/`query_results` are only called if the connected server actually advertises them. Write/finalize/preflight failures warn and are tracked (`getStats()`), never fail the run; `close()` tears down the spawned process and is always called, even if `finalize` failed. |
| `multiSink` | No | `createMultiSink([sinkA, sinkB, ...])` — fans `write()`/`finalize()`/`close()` out to every sink in the list, e.g. to run `markdownSink` and `mcpSink` together. |

### MCP results-sink server contract

Any local MCP server (spawned over stdio) can be used with `createMcpSink`
as long as it implements this tool contract. Only `store_result` is
required — `preflight`/`finalize`/`query_results` are optional, and
`mcpSink` feature-detects which ones a connected server implements via
`listTools()` (paginating through every page, not just the first). **v1
supports stdio transport only** — a locally spawned child process; remote/
shared MCP servers are deliberately out of scope for this release (`mcpSink`
normalizes its options into an explicit `{transport: {type, ...}}` shape
internally so a future transport can be added without redesigning the sink).

#### `store_result` (required)

```
input:  { testId, traceId, agentName, category, metric, score, pass,
          evaluator, runId, notes, recommendation, timestamp }
output: { content: [{ type: 'text', text: 'ok' }] }                         on success
        { isError: true, content: [{ type: 'text', text: '<reason>' }] }    on failure
```

`timestamp` (ISO 8601) is client-supplied and preserved by `mcpSink` at
write time; a server maps it to its own storage column/field as needed (the
Supabase reference server maps it onto that table's existing `created_at`
column — see its `src/server.js`). `store_result` is **at-least-once, not
exactly-once** — `mcpSink` does not retry in this release, but a server that
wants to dedupe on a future retry should treat `(runId, testId)` as the
natural idempotency key.

#### `preflight` (optional)

```
input:  {}
output: { content: [{ type: 'text', text: 'ok' }] } | { isError: true, content: [...] }
```

#### `finalize` (optional)

```
input:  { runId, agentName, totalRun, totalFail, byCategory }
output: { content: [{ type: 'text', text: 'ok' }] } | { isError: true, content: [...] }
```

#### `query_results` (optional)

```
input:  { testId?, agentName?, pass?, evaluator?, runId?,
          dateFrom?, dateTo?, limit?, cursor? }
```

All filter fields are optional and AND'd. `dateFrom`/`dateTo` are ISO 8601,
inclusive on both ends, compared against `timestamp`. `limit` is capped by
the server regardless of what the caller passes (recommended cap: 1000).
`cursor` is opaque and server-defined — returned as `nextCursor` in the
response when more rows remain, and passed back unchanged for the next page.

```
output (preferred): { structuredContent: { rows: [...], nextCursor?: string } }
output (fallback):  { content: [{ type: 'text', text: '{"rows":[...],"nextCursor":"..."}' }] }
```

A server that advertises an `outputSchema` for this tool **must** return
`structuredContent` — the MCP client SDK itself requires structured content
whenever a tool declares an output schema, so the text-JSON fallback only
applies to a server that does *not* declare one. `mcpSink.queryResults()`
parses in this order: check `isError` (throw with the reason if set) →
`structuredContent.rows` → a `text`-type content block parsed as JSON,
expecting `{rows: [...]}` (never a bare array) → an explicit
"malformed query_results response" error if none of the above match.

`mcpSink` exposes `queryResults(filter)` and an async
`supportsQueryResults()` predicate only when connected to a server that
implements this tool; `agent-test-kit results <agent>` is the CLI surface for
it (see the root `README.md` "Querying persisted results").

## Result row schema (fixed — every `resultsSink` receives exactly this shape)

```
{
  testId: string,
  traceId: string|null,
  agentName: string,
  category: string,
  metric: string,
  score: number|null,
  pass: boolean,
  evaluator: string,
  runId: string,
  notes: object|null,
  recommendation: string|null,
  timestamp: string (ISO 8601)
}
```

This shape is the package's own canonical contract, independent of where a
given repo chooses to persist it (console/local file/its own database) —
sinks vary only in destination, never in what fields exist.
